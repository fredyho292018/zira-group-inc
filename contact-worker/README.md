## API contract

`POST /api/contact` on the same origin as the website, `Content-Type: application/json`, `Origin` equal to configured `SITE_ORIGIN`, and `Idempotency-Key` containing a UUID v4 generated by the client. No credential or API key is required in the browser. No cross-origin CORS permissions are returned. Cookies are not used for authentication.

```json
{
  "fullName": "string",
  "email": "string",
  "phone": "string",
  "service": "string",
  "city": "string",
  "message": "string",
  "consent": true,
  "turnstileToken": "string"
}
```

Maximum JSON body: 16 KiB, enforced on actual streamed bytes as well as Content-Length. Name/city: 100 characters; email: 254; phone: 30 characters and 10–15 digits; description: 20–3,000 characters; token: 2,048. Service must match the seven UI options. Consent must be boolean true. Shared normalization uses NFC and trims surrounding whitespace. Control characters and header newlines are rejected; Unicode names and multiline descriptions are supported. Client validation supplements, rather than replaces, server validation. Unknown JSON properties are discarded.

| HTTP | Code | Meaning |
| --- | --- | --- |
| 200 | ACCEPTED | Provider returned a nonempty email receipt ID; same completed idempotency key returns the same confirmation |
| 400 | INVALID_JSON / INVALID_REQUEST_ID | Malformed request |
| 403 | ORIGIN_DENIED | Origin not approved |
| 404 / 405 | NOT_FOUND / METHOD_NOT_ALLOWED | Wrong path / method; Allow: POST |
| 409 | REQUEST_IN_PROGRESS / IDEMPOTENCY_CONFLICT | Existing pending request / key reused with different normalized data |
| 413 / 415 | PAYLOAD_TOO_LARGE / UNSUPPORTED_MEDIA_TYPE | Body limit / content type |
| 422 | VALIDATION_ERROR / TURNSTILE_INVALID | Field errors / failed, expired, mismatched or replayed challenge |
| 429 | RATE_LIMITED | Five new validly structured attempts per hashed IP per ten minutes; Retry-After: 600 |
| 502 | DELIVERY_FAILED | Provider rejected the message; no success shown |
| 503 | NOT_CONFIGURED / EDGE_CONTEXT_REQUIRED / SECURITY_UNAVAILABLE / SERVICE_UNAVAILABLE | Closed release gate or unavailable service |
| 503 | DELIVERY_UNCERTAIN | Provider acceptance cannot be established; no automatic resend |

Success: `{ "ok": true, "code": "ACCEPTED", "requestId": "same UUID" }`. Error: `{ "ok": false, "code": "controlled code", "fieldErrors": { "email": "Enter a valid email address." } }`; fieldErrors is present only when applicable. Responses are no-store and contain no provider diagnostics, credentials or personal data. SUCCESS means provider acceptance, not proven inbox delivery; delivery/bounce webhooks would require a later integration.

## Worker and security design

Workers fit this static Astro site: a future route for `/api/contact` can execute at the Cloudflare edge without changing Caddy or the Tunnel. `wrangler.jsonc` intentionally has no routes, public workers.dev URL, account ID or secrets; CONTACT_ENABLED=false and EMAIL_PROVIDER=unselected. It is preparation only, not a deploy command.

The Worker checks its release gate, HTTPS origin, privacy policy URL, provider choice and configuration before any external call. It accepts the edge's CF-Connecting-IP, never X-Forwarded-For. The edge must be the direct public entry point. A secret-key HMAC hides raw IPs and hashes normalized submissions. One SQLite-backed Durable Object coordinates rate limits and request receipts using storage transactions across isolates. This is suitable for a low-volume corporate contact endpoint; a high-volume service should partition coordination and validate quotas/costs before release. Neither in-memory counters nor eventually consistent KV are used for duplicate protection.

Turnstile Siteverify is called server-side with a secret and bounded timeout. Success, the expected hostname and action=contact must all match. Tokens are single-use and expire after five minutes according to [Cloudflare's server validation documentation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/). A duplicate already accepted with the same payload returns its stored receipt without attempting to redeem a consumed token again. Invalid challenges count toward the persistent limit. Origin checks are a browser defense, not authentication; rate limits and Turnstile are still mandatory. Future edge/WAF limits should also cover malformed request floods before activation.

Receipts contain only keyed fingerprints, status and expiry; IP buckets contain only keyed identifiers, counts and expiry. Alarms remove expired entries; request retention is 24 hours and rate windows are ten minutes. No message body, email, phone, token or raw IP is persisted in the Worker. The notification necessarily contains personal data at the chosen email provider and recipient mailbox: their retention/access policy must be included in the real privacy policy. Code performs no console logging and observability is disabled. Before activation, verify account-level tracing/log settings also exclude request bodies and headers.

Concurrent requests claim the same key transactionally: only one can call the provider. Email also carries the same provider idempotency key. Provider timeout, 5xx, incomplete confirmation or a crash never become success. Ambiguous receipts cannot be automatically resent; investigate acceptance with the provider before clearing a receipt. Pending records after a crash also require reconciliation. This intentionally prefers avoiding duplicates over blind retries. Deduplication lasts 24 hours and applies to one client-generated key; refreshing the browser, changing details or generating a new key is not a global duplicate guarantee. Do not retry an ambiguous request after retention expires without reconciliation.

## Email preparation

Provider selection remains pending. An isolated REST adapter for **Resend** is implemented as a candidate, based on its [send-email API](https://resend.com/docs/api-reference/emails/send-email) and [idempotency support](https://resend.com/changelog/idempotency-keys). No SDK/dependency, account or live key was added. Selecting another provider requires replacing this adapter and updating its tests; setting arbitrary EMAIL_PROVIDER values cannot enable delivery.

Text-only notification includes full name, validated email, phone, service, city, description, consent confirmation and UTC reception time. The configured verified mailbox is the sender; the customer's validated email is Reply-To only. Subject is fixed; user input never enters HTML, sender or subject headers. EMAIL_TO remains unset; no recipient is assumed. HTML-looking content is transmitted as literal text, not executed or silently rewritten.

## Configuration and activation checklist — not executed

1. Approve and publish a real privacy policy identifying Zira's contact-data processing, purposes, service providers, retention and applicable contact channels. Verify the actual URL and content before setting both privacy URL variables. The code checks URL syntax; it cannot establish legal suitability or whether the document is real.
2. Confirm provider, verified sender and recipient explicitly. Any required sender verification/DNS changes need separate authorization; this task makes none.
3. Create a Turnstile widget restricted to the approved hostname(s), then store TURNSTILE_SECRET as a Worker secret. Never use test keys for a live release.
4. Store EMAIL_API_KEY, EMAIL_FROM, EMAIL_TO and a random IP_HASH_SECRET of at least 32 characters as Worker secrets. Do not put them in the website, wrangler vars, screenshots, logs or source control. Set SITE_ORIGIN to the one canonical HTTPS origin and PRIVACY_POLICY_URL to the reviewed real URL. www needs its existing redirect to that origin or a separately reviewed origin policy.
5. Install a pinned official Wrangler version and validate its schema/bundle and Durable Object behavior locally/staging. No CLI was installed here. Review Cloudflare plan support, quotas, WAF limits, data residency and privacy configuration. The current tests use a serialized storage double; Cloudflare runtime/staging validation remains required.
6. With separate deployment authorization, provision the Durable Object and a Worker route matching only the canonical `/api/contact`. Do not alter the Tunnel. Route creation is a remote configuration change and has not occurred.
7. With recipient/provider authorization, run a controlled real integration test; verify receipt and delivery, rejection, limits and retries. Review CSP if configured: Turnstile requires the documented challenges.cloudflare.com script/frame/connect permissions. Current Caddy is unchanged.
8. Enable CONTACT_ENABLED only after those checks. Rebuild the website with PUBLIC_CONTACT_ENABLED=true, PUBLIC_CONTACT_PRIVACY_URL and PUBLIC_TURNSTILE_SITE_KEY. These are public configuration only. Docker's current build receives no new environment configuration, so the current image remains disabled. Document a deliberate public build-variable mechanism before any future production activation; never inject provider secrets into a Docker build.

Two independent release gates prevent accidental collection: the UI fieldset remains disabled and does not load Turnstile until public configuration is explicitly enabled; the server returns 503 until its separate full configuration is enabled. No fake privacy link or pretend reception service is published.
